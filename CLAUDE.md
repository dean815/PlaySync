# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PlaySync is a terminal (CLI, menu-driven) application for managing music playlists across Spotify, Apple Music, and YouTube Music: converting a playlist from one platform to others, merging playlists into a deduplicated list, comparing playlists, plus analysis, export/import, backup, search/recommendations, and batch/sync operations.

There is no test suite, linter config, or CI pipeline in this repo.

## Running the app

```bash
pip install -r requirements.txt
python main.py
```

Requires a `.env` file in the root with:
```
SPOTIFY_CLIENT_ID=...
SPOTIFY_CLIENT_SECRET=...
APPLE_MUSIC_DEV_TOKEN=...
APPLE_MUSIC_USER_TOKEN=...
YOUTUBE_AUTH_FILE=path/to/youtube_auth.json
```
- Spotify redirect URI must be registered as `http://127.0.0.1:8888/callback`.
- `YOUTUBE_AUTH_FILE` is generated by running `ytmusicapi setup` (see README for details).

Since all three clients authenticate on construction (`main()` instantiates `SpotifyClient()`, `AppleMusicClient()`, `YouTubeMusicClient()` up front), the app cannot run at all — even to test a single-platform feature — without valid credentials for all three services in `.env`.

## Architecture

- **`main.py`** — entry point and all interactive menus (`input()`-driven). Holds the `clients` dict (`{"Spotify": ..., "Apple Music": ..., "YouTube Music": ...}`) that every operation is threaded through, plus the core cross-platform flows: `convert_playlist`, `merge_playlists`, `compare_playlists`. Also defines `get_tracks` / `add_to_target`, thin wrappers that dispatch to whichever client is relevant and log timing/progress.
- **`spotify_client.py` / `apple_client.py` / `youtube_client.py`** — one client class per platform (`SpotifyClient`, `AppleMusicClient`, `YouTubeMusicClient`). Each independently implements the same informal interface: `get_playlist_tracks`, `create_playlist`, `add_tracks`, `analyze_playlist`, `export_playlist`, `import_playlist`, `delete_playlist`, `rename_playlist`, `duplicate_playlist`, `search_tracks`, `get_user_playlists`, `backup_playlists`, `create_playlist_from_search`, plus a recommendations method (`get_recommendations` for Spotify, `get_playlist_recommendations` for Apple/YouTube). There is no shared base class — the contract is duck-typed, so when adding a method to one client, mirror its name/shape across all three (`utils.py` and `main.py` call these interchangeably via the `clients` dict without checking platform type in most places).
- **`utils.py`** (`PlaylistUtils`) — static-method utility class for operations that span multiple platforms/playlists at once: batch conversion, cross-platform analysis/report generation, smart playlists with filters, sync rules, and collection export. Depends only on the duck-typed client interface above, not on any concrete client class.

### Track representation

Tracks are plain dicts, not a model class, and the shape differs slightly by context:
- Canonical/output shape (from `get_playlist_tracks`, used for dedup/compare): `{"name", "artist", "album"}` (Spotify adds `"id"`).
- Search results add fields like `"duration_ms"`/`"duration"` and `"popularity"` depending on platform.
- Merge/compare identity is `(track['name'], track['artist'])` — matching is name/artist string equality only, no ISRC or fuzzy matching (see README Limitations).

### Cross-platform track matching

Since each platform has its own IDs, `add_tracks` on the Spotify and YouTube clients re-search their own catalog by `"{name} {artist}"` for every incoming track to resolve a platform-specific ID before adding it. Apple Music's `add_tracks` is a no-op simulation (prints and counts, doesn't actually call the API) because real catalog ID lookup isn't implemented — see README Limitations. Keep this in mind before assuming a "successful" Apple Music conversion actually added tracks.

### Error handling pattern

Client methods generally catch exceptions internally, `print()`/log the error, and return `None`/`False`/`[]` rather than raising — callers check the falsy return value. `main.py`'s `get_tracks`/`add_to_target` additionally use the `logger` (module-level `logging.Logger` named `"playsync"`) for timing and progress instead of `print()`. When touching these paths, match the existing convention in the function you're editing rather than mixing print/logging styles.

## Known limitations (see README for full list)

- No ISRC-based matching — cross-platform track identity relies on exact name/artist string match.
- Apple Music track addition is simulated, not real, due to catalog ID lookup complexity.
- Minimal error handling/retry logic beyond the catch-and-return-falsy pattern above.
